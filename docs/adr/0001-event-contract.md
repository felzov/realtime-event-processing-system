# ADR 0001 — Event contract

- **Status:** Accepted
- **Date:** 2026-11-18

## Context

The pipeline needs one concrete event before anything else can be built: the ingest API validates
it, the broker partitions it, the consumer deduplicates it, and the aggregate is defined by it.
Several later guarantees depend on fields in this contract:

- Delivery is at-least-once (CLAUDE.md invariants), so every event needs an identity that survives
  client retries, producer retries and consumer redelivery.
- Windows are decided by event time, so the event must carry a time the client observed, separate
  from the time the server received it.
- Ordering exists only within a partition, so the partition key decides which events can be
  processed in order.
- The schema will change, and producer and consumer cannot always be deployed at the same instant.

The use case is deliberately narrow: one event type, one aggregate. The commercial idea behind the
project is unvalidated, so the contract does not try to be generic.

## Decision

1. **Use case.** The only event type is `order.placed`. It feeds one aggregate: per store, per
   currency, per 1-minute window, the number of orders (`order_count`) and their total amount in
   minor units (`revenue_minor`). The aggregate key is `(store_id, currency, window_start)`.
   Windows are tumbling, aligned to whole UTC minutes, and assigned by `occurred_at` (event time):
   `window_start` is `occurred_at` truncated to the minute, and a window covers
   `[window_start, window_start + 1 min)`. What happens to events that arrive late is decided in
   ADR 0005, not here.
2. **Envelope v1.** Every event has exactly these fields:

   | Field            | Type and rule |
   |------------------|---------------|
   | `event_id`       | UUID. Generated by the producer (the client), once per event, and reused on every retry of that event. It is the deduplication key. |
   | `event_type`     | String; a known type (`order.placed`). |
   | `schema_version` | Integer; a version supported for that `event_type` (decision 6). |
   | `occurred_at`    | RFC 3339 timestamp **with** a UTC offset. A timestamp without an offset is rejected, not assumed to be UTC. Normalised to UTC on parsing. |
   | `source`         | 1–64 characters of `[a-z0-9._-]`; names the producing system. |
   | `payload`        | Object; validated by the schema for `(event_type, schema_version)`. |

   Validation is strict: unknown fields are rejected at every level, types are not coerced (a
   string `"5"` is not an integer), and the encoded body is limited to 16 KiB. The events carry no
   personal data (no customer names, emails or addresses).
3. **Payload `order.placed` v1.**

   | Field          | Type and rule |
   |----------------|---------------|
   | `order_id`     | String, 1–64 characters. Informational; deduplication uses `event_id`, not `order_id`. |
   | `store_id`     | String, 1–64 characters of `[a-z0-9_-]`. |
   | `amount_minor` | Integer, `0 ≤ amount_minor ≤ 10_000_000_000`. JSON `true`/`false` is rejected even though Python's `bool` is a subclass of `int`. |
   | `currency`     | ISO 4217 code: exactly 3 uppercase letters. |

   Amounts are integers in minor units (cents), never floats, so sums are exact. The upper bound
   keeps one window's `revenue_minor` far from the `BIGINT` limit: it would take about 900 million
   maximum-size orders in one store-minute to overflow.
4. **Processing time is server-set.** The ingest API records `received_at` when it accepts an
   event. Clients cannot send it (it is not an envelope field, so strict validation rejects it).
   It is used for observability and for measuring lag, never for windowing. How it travels with
   the event (a broker header or a field added by the server) is decided with the producer in
   ADR 0003.
5. **Partition key is `store_id`.** While the topic's partition count stays the same, all events
   of one store go to one partition, so they are consumed in the order they were written. (The
   default partitioner hashes the key modulo the partition count, so adding partitions moves
   stores.) Nothing in the code may assume order across stores.
6. **Versioning.**
   - There is one topic per event type, `orders.placed.v1`. Every message on it carries
     `schema_version`, and a consumer supports the current version N and the previous version N−1.
   - An **additive** change (a new optional field) keeps the version number. Because validation is
     strict (decision 2), the consumer is deployed with the new field before the API accepts it.
     The API is the only producer, so this deployment order is something the project controls.
   - A **breaking** change (removing or renaming a field, changing a type or meaning) bumps
     `schema_version`. The consumer that understands N and N−1 is deployed first, then the API
     starts writing N.
   - The `.v1` in the topic name changes only if the topic itself must change in a way that cannot
     happen in place: a different partition key or a different partition count. Either one changes
     which partition holds a store, so per-store order would break between events already in the
     topic and new ones.
7. **Rejections use stable codes and never echo input.** An invalid event is rejected with a
   reason code from a fixed set (`missing_field`, `unknown_field`, `invalid_type`, `out_of_range`,
   `invalid_format`, `naive_datetime`, `unknown_event_type`, `unsupported_schema_version`,
   `body_too_large`, `invalid_json`) and the path of the offending field. The message never
   contains the submitted value, so a payload cannot leak into logs or responses through an error.
   The codes live in `src/event_pipeline/domain/errors.py` (phase 1, slice 4); this list is their
   specification.

**Update 2026-11-18 (phase 1, slice 4):** writing the parser showed four places where "strict"
needed a precise rule. Each is enforced in `src/event_pipeline/domain/events.py` and tested.

- `occurred_at` must match the RFC 3339 date-time grammar: `YYYY-MM-DDThh:mm:ss`, an optional
  fraction, and `Z` or `±hh:mm`; `T` and `Z` may be lowercase, as RFC 3339 allows. Pydantic on its
  own also accepts Unix seconds as a string (`"1763467230"`), a missing seconds field and a space
  instead of `T`; those are rejected with `invalid_format`. The offset `-00:00` means "offset
  unknown" in RFC 3339, so it is rejected as `naive_datetime`. A timestamp whose UTC equivalent
  falls outside the years 1–9999 is rejected as `out_of_range` instead of crashing the parser.
- A JSON object that repeats a key is rejected with `invalid_json`. A JSON parser keeps the last
  value, so `"amount_minor": -5, "amount_minor": 7` would otherwise pass as 7 and the invalid value
  would never be checked.
- `order_id` may not contain control characters (U+0000–U+001F, U+007F). PostgreSQL `text` cannot
  store U+0000, so such an event would otherwise pass validation and fail later, while being
  applied.
- For `unknown_field`, the reported path is the object that contains the unknown key, not the key
  itself: the key name is client input and is not echoed.

**Update 2026-11-19 (phase 1, slice 3):** "the default partitioner" in decision 5 depends on the
client. The broker spike showed that librdkafka's default (used by `confluent-kafka`) puts keys on
different partitions from the Java client's. Every producer therefore sets the murmur2 partitioner
explicitly, so a key maps to the same partition as with Kafka's own tools
([ADR 0002](0002-broker-and-client-stack.md), decision 3). The rule in decision 5 is unchanged: the
partition is the key's hash modulo the partition count.

**Update 2026-11-19 (phase 2, slice 2):** decision 4 is settled by
[ADR 0003](0003-ingest-acknowledgement.md), decision 4: `received_at` travels as a Kafka header,
so the message value stays the client's bytes.

**Update 2026-11-22 (phase 3, slice 2):** decision 1's aggregate key is unchanged as a set of
columns, but the table's primary key stores it in the order `(store_id, window_start, currency)`.
The primary key is the table's only index, and the query API reads one store over a range of
`window_start`, sorted by `window_start` then `currency`: in this order that is one index range
scan, already sorted. Deduplicating and upserting do not depend on the order.

## Consequences

- A client that retries after a timeout must resend the same `event_id`. A client that generates a
  new UUID per attempt defeats deduplication, and the order is counted twice. This is the client's
  side of the at-least-once contract and must be stated in the API documentation.
- Per-store ordering means one very busy store loads one partition (hot-store skew). Accepted for
  this project; the alternative keys below lose per-store order.
- Aggregates are per currency. Totals across currencies would need exchange rates, which are out of
  scope.
- The strict, no-coercion validation rejects some inputs a lenient API would accept (`"5"` for
  `5`, a timestamp without an offset). Errors are explicit instead of guessed.
- Supporting N and N−1 means each breaking change keeps an old parser alive until all events of
  version N−1 have left the topic's retention window and will not be replayed.
- The 16 KiB body limit and the amount bound are part of the contract. Raising either one is a
  contract change and goes through this ADR.

## Alternatives considered

- **Server-generated `event_id`.** The server would give the event an identity only after receiving
  it, so a client retrying after a lost response would create a second event with a new id.
  Deduplication would not catch it. Rejected.
- **Deduplicating on `order_id`.** It would fold together two legitimate events about the same
  order (relevant if more event types are added) and ties identity to a business field. Rejected;
  `event_id` identifies the delivery, `order_id` the order.
- **Processing-time windows.** Simpler (no late events), but a replay or a consumer that is behind
  would put events into the wrong minute, so the aggregate would depend on when it was computed.
  Rejected by the project invariants.
- **Partition key `event_id` or round-robin.** Even load across partitions, but no ordering for any
  store, and per-store order is the only ordering this design offers. Rejected.
- **Partition key `(store_id, currency)`.** Possibly a better spread, but splits one store's events
  across partitions for no current benefit. Rejected; revisit if skew is measured.
- **A topic per schema version** (`orders.placed.v1`, `orders.placed.v2`, … for every version).
  Each breaking change would need a new topic and a consumer reading two topics, with no order
  between them. Rejected in favour of `schema_version` inside one topic.
- **A schema registry (Avro or Protobuf).** Enforces compatibility automatically, but adds a
  service and a serialisation format to learn and run for one event type. Rejected for this
  project's scope; JSON validated by Pydantic is enough.
- **Floats or decimal strings for amounts.** Floats lose precision on sums; decimal strings need
  parsing and a scale per currency. Integer minor units avoid both. Rejected.
